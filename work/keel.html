Currently building

Keel

A durable, guard-railed agent harness for refund and support operations at small stores. One request path covers the agent loop, tool execution, RAG, skills, guardrails, approvals, traces, and evals. The plan is written; M0 is done.

Build plan · M0 done TypeScript Node 22 PostgreSQL Drizzle pgvector Zod Vitest Docker pnpm Biome

The problem

A support agent gets a message: “Order #4821 arrived damaged. I want a refund.” Answering it well means reading the store’s refund policy, checking the order and the customer’s history, deciding between a refund, a partial refund, a rejection, or an escalation, and then moving money exactly once. A model can do the reading and the proposing. The hard part is everything around it: a process that can die mid-run, a model that can repeat a tool call, customer text that can carry an injection, and a refund that must not happen twice.

Most agent demos stop at the loop. Keel treats the loop as one part of a system where every action is validated, persisted, and attributable. The model proposes; policy, row locks, and idempotency keys decide.

Each module has a narrow interface. The model returns a tool call or a final answer and nothing else. The dispatcher owns validation and idempotency. RAG returns chunks with document ids and versions. Skills are markdown bodies loaded by name. Guardrails run before the model, before an action, and after the model’s answer. The approval gate is a persisted state, not a blocking request. The trace records every one of those decisions.

A run is a persisted state machine. Killing the process while a run waits for approval does not lose it; approve or reject resumes from the step log.

The step log is the source of truth. The loop loads the last persisted state, asks the model for the next step, validates and dispatches it, then persists the result before moving on. Restarting the process resumes from the log instead of replaying side effects.

What it is built to survive

  • Crash after the refund succeeds, before the result is saved: resume finds the idempotency key and does not refund again.
  • The model emits the same tool call twice: the second call is deduped, not executed.
  • The model emits invalid arguments: the Zod error goes back to the model as a tool result, and the step is still counted.
  • The model loops without progress: a step, cost, or wall-time budget stops the run and marks it failed with a reason.
  • Injection in a customer message or order note: the guardrail logs it and the outcome does not change.
  • A refund above the threshold: the run pauses and no money moves until a human approves.
  • An approval is rejected: the run ends rejected and drafts a reply without a refund.
  • A policy document changes mid-run: the run keeps the version it started with.
  • The provider returns 429 or 5xx: bounded retries with backoff, then a clean failure.

Design decisions

The run loop is durable and event-sourced

runs and steps are the truth. Every loop iteration appends one step with a unique (run_id, seq). The loop stops on a final answer, max steps, max cost, or max wall time. A crash loses nothing but the current step; restarting reads the log and continues from the last persisted state.

A model turn has exactly two outcomes

ModelProvider.step() returns tool_call or final. Streaming, retries, persistence, and tool execution live outside that interface. Errors throw and are handled by the loop. The result is a small state machine where every step can be persisted and the provider can be replaced by a scripted mock.

Exactly-once is a unique key, not a promise

The dispatcher derives an idempotency key from hash(run_id, step_seq, tool, canonical_input) and stores it with the tool call under a unique constraint. The dangerous window is between the external call succeeding and the result being saved. On retry the key is already there, so the stored result is returned instead of moving money again. That makes the guarantee at-least-once delivery plus idempotent effects.

Guardrails sit outside the model

Input rules catch injection patterns, redact PII before logging, and reject out-of-scope cases. Action rules enforce per-tool scopes, refund limits, and velocity limits. Output rules check the schema, require a policy citation, and reject an answer that contradicts a tool result. Every verdict is written to guardrail_events. Asking the model to “ignore malicious instructions” is not a guardrail.

Approval is a persisted pause

A money tool above the threshold sets the run to awaiting_approval and records the request against the tool call. Approve or reject through the API resumes the loop from the step log; requests expire. Nothing blocks a worker while a human thinks, and a restart does not drop the pending decision.

Retrieval is hybrid and cited

Policy documents are chunked, embedded into pgvector, and indexed as tsvector. Vector and full-text results are merged with reciprocal rank fusion and reranked. search_policy(query) returns chunks with document ids and versions, and a final answer must cite chunk ids. A pure vector search would miss exact identifiers like “policy 3.2” or an order number.

Skills load on demand

Skills are markdown files with a name, a description, and a body. Only names and descriptions sit in the base prompt; load_skill(name) pulls the body in when the case needs it. Three start the set: damaged-item-refund, late-delivery, and suspected-abuse. Prompt size stays flat as the skill library grows, and the run records which skills it loaded.

Traces and evals are part of the harness

A trace records steps, tool calls, retrieved chunks, loaded skills, guardrail events, cost, and latency. A stored run can be replayed against the scripted provider using its recorded outputs. The eval suite covers the happy path, policy edges, injection, duplicate requests, crash-resume, and approval timeout. A prompt change has to show its eval delta before it merges.

Build plan

The plan is layered. Each milestone ends with something that runs; only start the next when the previous “done when” is true. Stopping after any layer still leaves a usable piece.

Layer 1 — the loop M0–M2

M0

Skeleton Done

Strict TypeScript, Node 22, Drizzle and Postgres, Zod, Vitest, and Biome. The model interface and a ScriptedProvider with a test that feeds a three-step script and gets the expected output.

M1

Durable loop Next

runs and steps tables, an append-only step log, and the loop: load state, call the model, persist the step, validate and dispatch, repeat. Stop conditions and two toy tools. Done when a test kills the loop after step 2, restarts it, and the run completes without redoing steps 1–2.

M2

Tool layer Planned

Registry, Zod input and output validation, error shaping back to the model, retries for transient failures, and the idempotency key with its unique constraint. Real store tools read a mock orders and payments backend. Done when the same issue_refund call, including after a simulated crash between the money moving and the result being saved, refunds once.

Layer 2 — context and control M3–M5

M3

RAG tool Planned

Chunk and embed policy docs into pgvector with a tsvector column, merge vector and full-text results with reciprocal rank fusion, then rerank. search_policy returns doc and version citations. Done when a 20+ question eval set records its recall@5.

M4

Skills Planned

Markdown skills with frontmatter, an on-demand loader, and three starting skills. Only names and descriptions live in the base prompt, and the run records what it loaded. Done when a damaged-item case loads only its skill and prompt size stays flat as skills are added.

M5

Guardrails and approvals Planned

Input, action, and output rules with every verdict stored. A refund above the threshold pauses the run until an approve or reject call resumes it. Done when an injection hidden in an order note changes nothing and a large refund blocks until approval.

Layer 3 — evidence M6–M7

M6

Traces and evals Planned

A per-run trace, replay of stored runs against the scripted provider, and an eval suite of about 30 cases. Metrics: decision accuracy, policy-citation rate, unsafe-action rate, and cost per case. Scripted evals run in CI. Done when a prompt or skill change shows its eval delta before merge.

M7

Polish Optional

An approval queue and trace viewer, provider fallback and a circuit breaker behind the model interface, multi-turn follow-ups, and the final write-up with recorded eval results.

Current status

This is a build plan with a working first milestone, not a shipped system. M0 is complete: the repository has strict TypeScript, Drizzle and Postgres scaffolding, Biome, Vitest, and a tested model interface with a scripted provider. There is no API layer and no run loop yet; M1 is next. The repository is not public yet, so this page is the build log for now.

The plan deliberately reuses lessons from the other projects: the LLM Gateway for budgets and provider fallback, GateKeep for hashed one-time links and signed URLs, IdleForge for outbox delivery. The new material is the durable agent loop, the guardrail and approval spine, and the eval harness.

The first honest proof is M1’s crash-resume test, followed by M2’s exactly-once refund. Nothing on this page claims those exist yet.

What I’d do next

  • Build M1 and its kill-after-step-2 test; a resumed run must not redo a completed step or repeat a side effect.
  • Build M2 and prove the crash window: a refund that succeeds before its result is saved still refunds once.
  • Do M3 next and record recall@5 before touching prompts. Without a retrieval number, a policy answer is just a guess.
  • Take M4 and M5 together; skill selection and approval thresholds both need the tool layer to be stable first.
  • Finish with M6. A baseline eval table is the only credible way to claim the agent got better, and M7 stays optional until then.
