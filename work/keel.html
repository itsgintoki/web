Design study

Keel

An operations agent for a small online store: it reconciles settlements against orders, investigates the mismatches code cannot resolve, and issues refunds through a path that moves money exactly once. Reconciliation is plain code. The model is the most expensive and least trustworthy part of the system, so it only ever sees the leftovers.

The problem

A store takes payments through a provider. Every night the provider sends a settlement file: what it actually paid out, net of fees, often batched, sometimes late, occasionally duplicated. Some rows match an order exactly. Others differ by a fee, arrive twice, arrive short, arrive for an order that never existed in the store's books, or match two orders that happened to cost the same amount on the same day.

That last part is where most reconciliation tools give up and hand everything to a person. It is also where a model is genuinely useful: given one exception, it can read the order, the payment, the customer's history and the refund policy, then propose a resolution with a citation. What it cannot be trusted with is deciding that money should move, and it certainly cannot be trusted to guarantee it moves once.

Most agent demos stop at the loop. Keel treats the loop as one component inside a system where every action is validated, persisted, and attributable. The model proposes; policy, row locks, and idempotency keys decide.

Each module has a narrow interface. The model returns a tool call or a final answer and nothing else. The executor owns validation and idempotency. Retrieval returns chunks with document ids and versions. Skills are markdown bodies loaded by name. Guardrails run before the model sees input, before an action executes, and before an answer ships. Approval is a persisted state, not a blocking request.

A refund intent is a row, not a call. The state write and the ledger row commit together. A provider timeout lands in unknown — not failed — until the provider is asked what actually happened.

Cases the design answers

  • The provider times out mid-refund. The intent is unknown. The executor queries the provider by its own key before it decides anything, because a timeout is not a failure.
  • The same refund is fired ten times at once. One effect. The key comes from the exception, not from the call, so a retry cannot become a second refund.
  • Ten different refunds race against the daily cap. The cap holds, because the reservation is an UPDATE ... WHERE total + amount <= cap, not a read followed by a write.
  • The process dies after the money moved. Restart finds the key and the ledger row and does not refund again.
  • The same key arrives with a different amount. Rejected, not replayed. Returning a cached success for a different request is how a store loses money and its audit trail at once.
  • Two orders, same amount, same day. Reported as ambiguous instead of being silently matched, and the matcher is ordered deterministically so the answer does not change between runs.
  • A settlement arrives twice, or out of order. Deduped on the provider's reference at reconcile time, before any model is involved.
  • Injection in a customer note or a settlement description. Logged. The guard that stops the action is code, not a sentence in the prompt.
  • A refund above the cap. Nothing moves until a human approves, and pending requests expire instead of waiting forever.
  • A tool call with invalid arguments. The Zod error goes back to the model as an observation and the step still counts against the budget.

Design decisions

Reconciliation is plain code; the model sees only exceptions

Matching keys, date windows, fee handling and duplicate detection are deterministic functions with tests. The agent is invoked once per exception, not once per row. That keeps cost proportional to the number of problems rather than the number of transactions, and it keeps the model out of the part of the system where a wrong answer is silent.

A model turn has exactly two outcomes

ModelProvider.step() returns tool_call or final. Streaming, retries, persistence and tool execution live outside that interface. Tool failures come back as observations, not exceptions. The loop itself never throws: budget exhaustion, timeout or confusion return an outcome — propose, escalate, or fail with a reason — so the state machine has no unreachable branch.

Exactly-once is an intent plus a hash, not a promise

The key is derived from the business fact — refund:<exception_id> — so the model cannot choose it and a retry cannot invent a new one. It is stored with a hash of the canonical payload and a two-phase status. A completed key with a matching hash replays the stored response; a matching key with a different payload is a rejection; a live lock is a conflict the caller retries; an expired lock means the previous attempt died and its outcome must be reconciled with the provider before anything else happens. The result is at-least-once delivery with idempotent effects.

Limits are enforced inside the write

A refund cap checked with a SELECT sum(...) before an insert is check-then-act: ten concurrent requests read the same total and all pass. The reservation is a single conditional update on a per-day row, in the same transaction as the refund itself, and it is released if execution fails. Counting attempts instead of reserving budget is the conservative alternative — never an over-refund, occasionally a refused legitimate one. Either is defensible; not choosing is the bug.

Approval is a persisted pause

A refund above the cap leaves the intent in proposed and records a pending approval request. Approve moves it to approved; reject ends it; requests expire. Nothing blocks a worker while a human thinks, and restarting the process does not drop the pending decision.

The ledger is append-only by grant

The application role holds SELECT and INSERT on the ledger and nothing else. Append-only as a convention is a comment; append-only as a revoked privilege is an enforcement. Every row carries the actor — agent, human, or system — so a refund can be attributed later without trusting the trace.

Retrieval is hybrid and cited

Policy documents are chunked, embedded into pgvector, and indexed as tsvector. Vector and full-text results are merged with reciprocal rank fusion and reranked. search_policy(query) returns chunks with document ids and versions, and a proposal must cite chunk ids. Pure vector search misses exact identifiers like “policy 3.2”; pure keyword search misses paraphrase. A citation that does not exist blocks auto-approval rather than becoming a footnote.

Skills load on demand

A skill is a markdown file with a name, a description and a body. Only names and descriptions sit in the base prompt; load_skill(name) pulls the body in when the case needs it. Prompt size stays flat as the library grows, and the trace records what was loaded — which is also what makes a skill change reviewable.

Agent-written code runs in a sealed container

Settlement files from small providers are inconsistent, so the agent can write a parser. It runs with no network, a read-only root filesystem, dropped capabilities, memory and PID limits, and a wall-clock timeout that kills and reaps the container. The output directory is created and owned by the container's uid, because a bind mount is only writable if the host agrees. Standard output is treated as untrusted data, because a model wrote it and a model will read it.

Failure is injected on purpose

The fake payment provider has a flaky mode: random latency, 5xx responses, duplicate acknowledgements. Idempotency that has only been tested against a cooperative provider has not been tested. This belongs next to the executor, not at the end of the project, because the bugs it finds are in the code it exercises.

What this costs

  • More moving parts than a refund queue. Reconciliation, guards, a ledger, a trace and a sandbox all have to exist before the first refund is credible. The payoff is that every decision is replayable and attributable, which a queue does not give you.
  • Docker shares the host kernel. That is acceptable for parser code over a file the store owns. It would not be acceptable for hostile code, where the answer is gVisor or a microVM, and saying so is part of knowing what the sandbox is.
  • Retrieval is only worth it when policy actually changes. If the refund rule is five sentences, code the five sentences and skip the vector store. The retrieval layer has to earn its place by being wrong less often than a static rule would be.

Status

This is a written design, not a running system. The repository has no implementation yet and this page does not claim otherwise: no evals have been run, no refund has moved, and the numbers above describe the shape of the design rather than measured results.

The work starts with the reconciler, because it is deterministic and can be proved against a fixture of planted mistakes, then moves to the executor, where the concurrency and timeout tests are the first honest evidence that the money path is safe.
