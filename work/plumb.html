Plumb

A payment reconciliation and refund-ops service for the “charged, but the order failed” case. Verified ingest, an out-of-order-safe payment state machine, a reconciler, safe refunds, and a double-entry ledger. The plan is written; M1 is next.

The problem

A gateway debits the customer, then the store’s order stays pending or failed. Gateway webhooks arrive late, twice, out of order, or never, and small teams sort it out in spreadsheets. Razorpay’s webhook docs say duplicate deliveries are expected, tell you to dedupe on the event id, and warn that events may not arrive in order. Every store rebuilds this logic badly.

Plumb records every signal from the gateway and the store, derives the true state of each payment, finds mismatches, auto-resolves the clear ones with safe idempotent actions, and routes the rest to a reviewer. The LLM helps match a customer’s support message to the right payment; it never moves money.

Each layer has one job. Ingest trusts nothing until the signature passes. The state machine ignores arrival order. The reconciler compares derived payment state with order state. Resolution actions are locked, capped, and idempotent. The ledger and outbox are written in the same transaction as the action.

State only moves forward. A late authorized event after captured is recorded but ignored for state; terminal states are final.

What it catches

  • Paid, not fulfilled: the gateway captured but the order is pending or failed. Auto-mark the order paid when the amounts match.
  • Duplicate capture: two captures for one order. Auto-refund the extra up to the merchant’s cap; otherwise send it to a human.
  • Fulfilled, not paid: the order says paid but no capture was seen. Wait out the grace window, then escalate.
  • Amount mismatch: the captured amount differs from the order total. Always human.
  • Refund stuck: a refund started but no processed event arrived. Re-poll the gateway; auto-resolve only if confirmed.
  • Orphan payment: a captured payment with no matching order. The LLM can propose a match from the customer’s message; a human confirms.

Design decisions

Ingest is signature-first and append-only

The webhook route verifies HMAC-SHA256 over the raw request body, never the re-serialized JSON. It dedupes on the gateway event id, appends the untouched event, enqueues a BullMQ job, and returns 200 quickly. A bad signature stores nothing; ten parallel copies of one event produce one row and one job.

Payment state is derived, not overwritten

The state machine derives each payment’s state from its event stream in any arrival order. State only moves forward; a late authorized after captured is recorded but ignored for state. A version column with optimistic checks keeps concurrent derivations honest, and terminal states are final.

Reconciliation is a scan with occurrence records

A scheduled scan compares payment state with order state and writes one mismatch row per payment, type, and scan. The scan window is recorded once, so rerunning the same scan produces no duplicates. Each mismatch type has a seeded scenario and an exactly-right-row test.

Auto-resolution is locked, capped, and shadow-first

New merchants start in shadow mode, where Plumb proposes but never acts, until the numbers look right. In auto mode a refund executor locks the payment row, checks the refundable remainder, inserts the refund, and calls the gateway with an idempotency key. Twenty concurrent refund requests for one payment produce exactly one refund; a crash after the gateway call but before commit is recovered by the retry.

The ledger is double-entry, append-only, and checked

Every capture, refund, and fee becomes balanced ledger entries in the same transaction as the action. A database check rejects a transaction whose entries do not sum to zero. A nightly job compares ledger totals with the gateway’s settlement data; replaying all events must rebuild identical balances.

Outcomes leave through an outbox

Merchant gateway keys and webhook secrets are encrypted with AES-256-GCM and a key id for rotation. The resolution and its outbox row commit together; a relay worker sends HMAC-signed webhooks with backoff and a dead letter. Killing the relay mid-delivery cannot lose a committed resolution, and the store dedupes by id.

Redis is a projection; Postgres is the truth

The ops view of open mismatches is a Redis projection rebuilt from Postgres with a staging key, an atomic swap, and a completeness marker. A stale projection returns 503 rather than a misleading zero. A stdio MCP server exposes find_payment, list_mismatches, and propose_resolution behind the same auth and routing.

The LLM never moves money

A customer message such as “paid ₹1,499 yesterday, no order” goes through the LLM Gateway with one virtual key per merchant. The model extracts amount, time, email, or UTR; a deterministic query fetches candidate payments; the model must cite a candidate id, validated by Zod and a membership check. Routing still decides, and a wrong or invented match escalates to a human.

Build plan

The plan is layered. Only start a layer when the previous one passes its tests; stopping after any layer still leaves something shippable.

Layer 1 — core M1–M5

M1

Verified ingest + simulator Next

HMAC-SHA256 over the raw body, event-id dedupe, append-only events, a BullMQ job, and a simulator that duplicates, delays, and reorders signed events.

M2

Payment state machine Planned

Derive created, authorized, captured, failed, and refunded from events in any order. Forward-only state, optimistic version checks, final terminal states.

M3

Order sync + reconciler Planned

Register orders, update their status, and run a scheduled scan that writes mismatch rows by type. One scan window produces one set of rows.

M4

Safe resolution actions Planned

Routing, per-merchant caps, shadow or auto mode, a locked refund executor with an idempotency key, and approval records with TTL.

M5

Double-entry ledger Planned

Balanced capture, refund, and fee entries in the same transaction; an append-only zero-sum check; a nightly gateway settlement comparison.

Layer 2 — resume coverage M6–M9

M6

Gateway poller Planned

Scheduled pulls as poll events, missed-webhook detection, timeouts, transient retries, a circuit breaker, and cancellation on shutdown.

M7

Encrypted secrets + outbound webhooks Planned

AES-256-GCM with a key id, an outbox in the state-change transaction, HMAC-signed delivery with backoff and a dead letter.

M8

Reviewer links + evidence Planned

One-time links with hashed tokens, expiry, and burn-on-read; encrypted evidence served by signed URLs; reviewer and merchant-admin roles.

M9

Ops projection + MCP Planned

Redis projection with a staging key, atomic swap, and completeness marker; stale data returns 503. A stdio MCP server exposes read and propose tools behind auth.

Layer 3 — something more M10–M12

M10

Chaos + property-based tests Planned

Random delay, duplication, reordering, drops, and partial outages; fast-check event streams; invariants checked after every run.

M11

LLM ticket matching + evals Planned

Grounded extraction through the LLM Gateway, candidate-only matching with citation validation, a timeline summary, and 40+ labeled eval cases. The wrong-match rate is the headline number.

M12

Observability + delivery Planned

One OpenTelemetry trace from webhook to resolution, mismatch-age and auto-resolve metrics, Redis-backed per-merchant limits, a load test, and a Razorpay test-mode demo.

Current status

This is a build plan, not a shipped system. The repository is empty; M1 is the next step. The page will be updated as milestones land, and the first honest proof is the M1 duplicate-delivery test: the same event ten times in parallel produces one row and one job.

The plan deliberately reuses pieces from the other projects: the LLM Gateway for budgets and fallback, GateKeep for one-time links and signed URLs, and IdleForge for outbox delivery and Redis projections. The new material is webhook-level ingest, an out-of-order-safe payment state machine, a double-entry ledger, and reconciliation.

What I'd do next

  • Build M1 and its simulator; prove duplicated, delayed, and reordered events never create a second row or job.
  • Take M2–M5 in order: state machine, reconciler, locked refunds, then the ledger invariant.
  • After M4, run shadow mode against one small store’s test data before enabling auto-resolution. Real mismatches will teach more than seeded ones.
  • Do Layer 2 in order: M6–M8 first, then the projection and MCP server.
  • Do M10 before M11; the LLM headline only works if the property tests and eval set are credible. Finish with M12.
