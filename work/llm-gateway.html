LLM Gateway

A budget-controlled LLM API gateway with virtual keys, per-key usage accounting, and automatic Groq-to-Gemini fallback. Every request reserves estimated cost before it reaches a provider.

The problem

Putting an LLM behind an API key is easy. Keeping a budget correct while several requests share that key is not. A request can be rejected for lack of funds, then retried; a provider can time out after the caller has already been charged; a second provider can answer while the first request is still settling; and a client can disconnect after the reservation has been taken.

LLM Gateway treats the budget as a ledger, not a counter. It reserves an estimated cost in integer micro-USD before the provider call, commits that reservation, and settles the provider-reported usage afterward. Fallback and cancellation are part of the same accounting path.

The gateway exposes an OpenAI-compatible /v1/chat/completions endpoint. The caller only ever sees the virtual key; the provider credentials stay server-side.

Design decisions

Reserve first, settle after the provider responds

A request cannot spend money it has not reserved. The gateway takes a row lock on the key balance, rejects the request if the worst-case estimate does not fit, and writes the reservation before calling a provider. Provider-reported usage then replaces the estimate with the settled amount.

Transactions never span a network call

The reservation transaction is short: lock, check, write, commit. The LLM call happens outside it, so a slow provider does not hold a database lock or block other requests on the same key. A crash between reservation and settlement leaves a recoverable record instead of a half-open transaction.

Integer micro-USD, not floating-point dollars

All balances and usage amounts are stored as integer micro-USD in PostgreSQL bigint. That removes the rounding drift that shows up when fractional cents are repeatedly added, subtracted, and compared under concurrency.

Fallback is a routing decision, not a blind retry

Transient primary failures get one retry with a short backoff. If Groq stays unavailable, the same reservation is routed to Gemini. A circuit breaker opens after repeated primary failures so later requests skip the timeout penalty. Non-transient client errors fail fast and do not trigger fallback.

Disconnects and abandoned reservations release budget

If the client closes the connection, the gateway aborts the upstream request and releases the reservation. A TTL sweeper reclaims reservations stranded by an ungraceful server exit, so budget is not lost to a process that never got to settle.

The important invariant: a request can fail, retry, fall back, or lose its client without letting the budget ledger drift.

The 11-test integration suite runs against real PostgreSQL with provider calls mocked; it covers budget exhaustion, the three-way TOCTOU race, fallback routing, usage accounting, and TTL recovery.

What I'd do next

  • Add streaming responses without letting a partial stream escape the reservation and settlement path.
  • Expose per-key latency, fallback rate, and spend as metrics so provider behavior is visible over time.
  • Add a second fallback adapter behind the same interface and test routing under mixed provider failures.
  • Push the concurrency tests beyond the current integration suite and measure contention on the key row.
