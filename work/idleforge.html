IdleForge

An idle-game economy backend with atomic offline collection, persisted idempotency, a transactional outbox, batched bonuses, an append-only ledger, and an exact Redis leaderboard.

TypeScript Node.js Express PostgreSQL Drizzle Redis BullMQ Vitest Docker

The problem

Idle games are full of small economy mutations: collect what was earned while offline, buy an upgrade, claim a reward, update a leaderboard. Those operations are easy to write once and surprisingly hard to keep correct when clients retry, jobs run twice, or two requests touch the same player at the same time.

IdleForge is built around the idea that the economy should stay consistent even when the request layer is not. The database is the source of truth; Redis and the queue are there for speed and scheduling, not to quietly become the ledger.

The API and workers run as separate processes. Both write through the same data model, so a worker retry and an HTTP retry hit the same guarantees.

Design decisions

Offline collection and upgrades are transactions

Collection and spending are guarded by SQL and row locks. A request either credits the correct amount and commits, or it fails without leaving a half-applied balance change. Two concurrent upgrades cannot spend the same currency twice.

Retries are expected, so idempotency is persisted

Client retries use persisted idempotency records instead of an in-memory cache. Manual bonuses are written to a transactional outbox before Redis, and the database occurrence primary key is the final duplicate-award guard. Redis job-ID deduplication is only an optimization.

Bonuses are batched and resumable

Each world-event run processes players in bounded batches with a persisted last_player_id cursor. A crash between batches resumes from the cursor; no committed batch is paid twice, and concurrent player writes are only delayed for one batch.

Every balance mutation writes a ledger entry

Collection, purchases, and bonuses insert append-only ledger_entries in the same transaction as the balance change. npm run ledger:verify asserts that the ledger sums to the current balance for every player.

Postgres owns the truth; Redis owns the fast view

The leaderboard is a Redis ZSET plus an exact-score hash, rebuilt from PostgreSQL keyset pages and published atomically. If Redis is unavailable, the API returns 503 rather than serving a stale or misleading ranking; rebuilding is a recovery path, not the primary write path.

Separate API and worker processes

HTTP traffic and background work have different failure modes, so they have separate lifecycles. Both emit correlation logs and expose health checks, and both handle graceful shutdown so in-flight work is not cut off mid-transaction.

The interesting part is not the happy path. It is what happens when the same economy mutation arrives twice.

Local run on 2026-11-08: 300 mixed requests at concurrency 10, 0 errors, p95 28.5 ms. A separate 600-request per-endpoint run measured p95 23.0 ms on /player/me and 22.2 ms on /leaderboard.

What I'd do next

  • Deploy the API, worker, and scheduler to Railway with managed PostgreSQL and Redis, then run the migration workflow.
  • Push the load test beyond 10 concurrent readers and measure where PostgreSQL row contention starts to dominate.
  • Run a real Redis-loss drill: assert the outbox reconciler re-dispatches the bonus and the leaderboard rebuilds.
  • Add monthly partitioning for the append-only ledger as volume grows.
